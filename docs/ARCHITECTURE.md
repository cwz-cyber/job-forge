# OpenHaven 智能体设计

## 1. 产品边界

OpenHaven 是“有证据约束的求职材料编辑器”，不是 RPA，也不是招聘网站客户端。

允许的能力只有：读取用户主动提供的候选人素材、JD、表单题目和投递记录；生成或改写文本；进行本地统计；等待用户人工确认。

明确不提供：网页访问、JD 链接抓取、浏览器点击、表单输入、附件上传、招聘接口调用、自动投递、代替用户联系 HR。这些能力不进入工具清单，因此即使提示注入要求执行，运行时也没有对应执行器。

## 2. 为什么不能只靠一段系统提示词

“不要编造”写在提示词里仍可能被模型违反。OpenHaven 使用四层约束：

1. **输入白名单**：候选人经历拆成不可变的 `Evidence`，每条有唯一 ID。
2. **结构化生成**：模型不能只返回自由文本；每个事实块必须声明 `kind` 并引用 `evidence_ids`。
3. **确定性后校验**：程序检查未知引用、新数字、敏感资历词、弱关联文本和字数上限；失败时携带具体错误重试，仍失败则拒绝输出。
4. **人工终审**：草稿不会自动进入“已确认口径”。只有用户明确确认后，才能写入同场招聘上下文。

这套机制能显著降低幻觉，但自然语言的语义真实性无法仅靠字符串规则得到数学意义上的绝对保证，所以人工终审仍然是发布前的硬门槛。

## 3. 组件结构

```text
用户输入
   │
   ▼
Request Validator ── 拒绝浏览器/投递/上传等越权动作
   │
   ├── Candidate Evidence Store（用户素材）
   ├── JD Evidence Builder（只处理粘贴文本）
   └── Confirmed Context（仅用户确认的同场口径）
   │
   ▼
Workflow Prompt Builder
   │  技术风格 / 体制风格 + 六类工作流模板
   ▼
LLM Adapter
   │  JSON: sections → blocks → evidence_ids
   ▼
Grounding & Length Guardrails
   │
   ├── 通过 → 草稿 + 字数 + 引用来源 → 人工终审
   └── 失败 → 最多一次定向修复 → 再失败则拒绝输出
```

对应代码：

- `models.py`：领域模型和输入/输出结构；
- `prompts.py`：底层约束、文风和工作流提示；
- `policy.py`：模型之外的确定性安全检查；
- `agent.py`：编排、修复重试和字数绑定；
- `storage.py`：人工确认上下文与投递台账；
- `llm.py`：可替换的模型适配器；
- `cli.py`：本地原型入口。

## 4. 素材库设计

候选人事实使用最小可引用粒度，推荐一条只表达一个可验证事实：

```json
{
  "id": "project.agent.action.01",
  "category": "project",
  "text": "实现了……",
  "origin": "candidate",
  "source_note": "2026-10-28 用户补充"
}
```

时间、职责、技术栈和成果数字不要混在一条超长素材里。新增、修改、删除素材应保留审计记录；生产版可增加 `created_at`、`supersedes`、`verified_by_user` 字段。

固定背景样例只写入用户已经给出的三项事实：本科计算机科学与技术、硕士机械工程、研究方向为自适应装配故障检测。意向、地区和岗位偏好是偏好字段，不能被模型改写成经历或技能。

## 5. 输出协议

模型输出的最小单元：

```json
{
  "text": "本科专业为计算机科学与技术。",
  "kind": "candidate_fact",
  "evidence_ids": ["education.undergraduate.major"]
}
```

`kind` 的含义：

| 类型 | 是否必须引用 | 可表达内容 |
|---|---:|---|
| `candidate_fact` | 候选人素材 | 经历、技能、成果、背景 |
| `jd_fact` | JD 素材 | 岗位门槛、职责、加分项 |
| `analysis` | 可引用 | 匹配分、比较、统计结论 |
| `advice` | 可引用 | 写作和投递建议 |
| `label` | 否 | 标题或非事实标签 |

对外展示时隐藏内部引用 ID，但保留在响应 JSON 中供用户展开核验。

## 6. 六类工作流

### JD 解析

输入粘贴的 `jd_text`。输出门槛、加分项、方向、软素质、匹配点、短板、可侧重素材、匹配分、关键词和推荐风格。匹配分是分析结论，不得被描述为招聘方评分。

### 网申作答

输入 `questions[]`，每题包含 `label`、可选 `hint`、可选 `max_len`。程序按原顺序绑定标题和上限，模型不能自行改题或合题。计数口径是非空白可见字符；“已压缩”作为元数据展示，不占网申正文。

### 简历定制

输入 JD、要改写的原段落或指定素材 ID。要求每一条事实都可回指素材。STAR 是组织方式，不是补全缺失 S/T/A/R 的理由。

### 面试材料

输入时长和岗位。自我介绍与参考回答受素材约束；“可能被问到的问题”和反问 HR 的问题属于建议，不得暗示候选人拥有未提供的经历。

### 投递台账

台账是确定性本地功能，不必交给模型保存。状态限定为：待投递、已投递、初面、二面、挂掉、offer。汇总可统计阶段分布和超过阈值未更新的岗位；跟进话术只是草稿，不会被自动发送。

### 求职信

输入 JD 和可选字数上限。正文只组合 JD 需求与候选人证据，不生成虚构称呼、招聘负责人姓名或公司业务事实。

## 7. 一致性与人工确认

同一个 `application_id` 代表同一家公司/同一场招聘。生成结果先处于 `draft`；用户核对后显式执行 `confirm_context`，保存已经确认的时间、职责、成果和偏好表述。后续生成会读取该上下文。

草稿绝不自动写入确认区，否则第一次模型错误会污染后续所有回答。素材本身发生修改时，应提示用户重新确认受影响的口径。

## 8. 推荐的产品界面

最小版本建议三栏：

- 左栏：素材库，按教育、科研、项目、实习、技能、奖项分类；
- 中栏：JD 或问题输入，以及技术/体制风格、字数、纯文本开关；
- 右栏：生成草稿、逐段素材引用、字数、风险提示、复制按钮和“确认口径”按钮。

复制按钮可以存在，但不能自动定位或写入招聘网站。素材不足的段落使用明确的警示色，并直接显示“素材无相关经历，建议填无”。

## 9. OpenViking 对接方案

OpenViking 当前把资源、记忆和技能组织在 `viking://` 虚拟文件系统中，并提供按 URI 范围检索的能力。OpenHaven 应把它当作**可审计的上下文仓库**，而不是让检索结果绕过素材校验。参考：[OpenViking 概念说明](https://docs.openviking.ai/en/getting-started/01-introduction)、[Retrieval API](https://docs.openviking.ai/en/api/06-retrieval)。

建议目录：

```text
viking://user/{user_id}/
├── resources/openhaven/
│   ├── candidate/                 # 用户确认的原始候选人素材
│   │   ├── education.json
│   │   ├── projects.json
│   │   ├── research.json
│   │   └── skills.json
│   └── applications/{application_id}/
│       ├── jd.md                  # 用户粘贴的 JD
│       └── confirmed-context.json # 用户明确终审后的口径
└── skills/openhaven/
    └── workflow.md                # OpenHaven 工作流说明
```

读链路：

1. 使用岗位关键词在 `candidate/` 子树内做限定范围检索，不做全库无边界召回；
2. L0/L1 只用于判断相关性，最终可引用事实必须回读 L2 原始素材；
3. 把原始素材 URI 和片段 ID 转换成 OpenHaven 的 `Evidence.id`；
4. 生成结束后继续执行本地 grounding 校验；检索命中不等于事实已验证。

写链路：

1. 新素材先进入待确认区，用户确认后才写入候选人资源；
2. 普通对话或模型草稿不得自动沉淀为候选人事实；
3. 只有“确认口径”动作可以更新 `confirmed-context.json`；
4. 投递台账与候选人事实分开存放，不能把“意向岗位”误召回成“从业经历”。

当前原型通过构造函数注入 `CandidateProfile`，这就是存储适配边界。接入时新增 `OpenVikingEvidenceRepository`，负责 URI 检索、L2 回读和 `Evidence` 映射即可；编排、提示词和校验层不需要依赖 OpenViking SDK 的具体版本。

## 10. 生产化路线

1. 用 SQLite/PostgreSQL 替换 JSON 文件，并增加素材版本、审计和加密；
2. 为每个工作流增加严格 JSON Schema 校验和快照测试；
3. 增加独立的语义核验模型，但只作为第二道检查，不能替代确定性规则；
4. 对姓名、电话、邮箱等个人信息做加密和日志脱敏；
5. 增加“逐条接受/拒绝”界面和导出纯文本功能；
6. 建立红队测试集：提示注入、虚构奖项、数字篡改、跨场次口径污染、超长回答、体制文风污染。
